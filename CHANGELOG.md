# Changelog

Every notable change to this project is recorded in this file.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and the project adopts [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

Entries up to 0.3.0 were condensed when the repository was translated to en-US: the fact
each one records is preserved, the reasoning behind it lives in the git history and in the
issues each entry cites.

## [Unreleased]

### Changed

- **An export carries the history of what it carries.** An archive of one folder arrived with the trail of the whole notebook, naming folders and notes that were not in it and carrying the **body of every revision those entries named** — so a Guidance deliberately left out of an archive travelled inside its history anyway. Under a selection, an entry about something the archive does not hold is now left out with it, an entry about the Guidance travels only when the Guidance does and one about a Template only when that Template does, while the entries about the life of the notebook always travel, because an import reads the old identifier of the notebook off them. The filter runs before a revision is fetched, so nothing is read from the object store for an entry that will be dropped. **The whole notebook still carries the trail whole**, the entries about notes that were deleted included: a deleted note travels nowhere else, so that archive is the one place they survive. The way in has always worked this way (RN-PRT-022, RN-PRT-023, RN-PRT-024). (#161)

- **An environment is delivered by a command again, and the pipeline is switched off rather than taken apart.** Delivery ran on AWS, in a CodePipeline per environment, and while the product is still moving weekly that esteira charged for every lesson twice: in money, where CodeBuild and CodePipeline were 63% of the account in September, and in the clock, where a defect took twenty to forty minutes to show itself and every correction started the queue again. `pnpm -C memorysmith-infra deliver` now raises an environment from the checkout it runs in — the SPA built once, the synth, the network and the hosting, the waits on DNS and on the sending identity, every other stack, and the smoke that asks each surface which version it serves — refusing any account but the one `cdk.json` names for that environment. A release is `release-checks`, then the delivery of production, then `publish-release`, and the tag is still written by the release App under the same ruleset: only where the command runs changed, never who signs it. **Nothing of the pipeline was deleted from the repository**: the stack is declared as it always was and its cases still hold it, the app instantiates it only when `cdk.json` names a connection, and writing that ARN back plus one `cdk deploy` raises it again. While it is off, `staging:start`, `staging:status` and `staging:destroy` say so and name what to run instead.

- **Exporting and importing start from Transfers, wherever you are.** Each half used to live on the single screen it was born on: the export was a button inside a notebook, so exporting meant navigating to the notebook first, and the import was a link on the dashboard, so importing meant going back there. Transfers is on every screen — beside the user menu, where a browser puts its downloads — and it is where a transfer is already followed, downloaded again and deleted, so it is where one is started. A new export asks which notebook, among the ones you can see, and what goes in the archive; an import opens the page that reads the file and shows what it will create. The icon no longer disappears when nothing has ever been transferred, and the two entry points that were elsewhere are gone (RN-PRT-019, RN-PRT-020). (#151)

- **An export can carry the whole history of a notebook, and an import brings it back.** An archive used to be the notebook as it stood: the body in force of each note, the Guidance, the folders and their Templates. Since deleting a notebook now takes its trail with it, an export is where a history survives on purpose — so the export asks, and when it is asked it carries the entries **and the content of every revision they name**, because a history you cannot read says that something was written and never what. The archive is larger for it, and a kept export counts towards the storage of the plan, which the page says where the choice is made. An import brings those entries back as entries of your subscription, keeping the person and the instant each one carried, re-keyed onto the notebook it creates: the history of an imported note lists who wrote it and when, and reading it as it stood on a date answers the body it had then. The history is one more item of the import, ticked like the Guidance, and the `Structure only` preset is gone with it — the Guidance and the Template of each folder are items of the tree, so the preset was a selection anybody can make by hand. The document format goes from `1.0` to `1.1`, and an archive of either version still imports (RN-PRT-017, RN-PRT-022, RN-PRT-023). (#150)

- **Deleting a notebook takes with it the record of what happened inside it.** The trail used to outlive the notebook whole: the product stopped serving the history of each note, because what those entries pointed at had been destroyed, but every line of who wrote what and when stayed stored and readable through the activity of the notebook. Now the purge that destroys the content destroys those entries too, and what the subscription keeps is the **life** of the notebook — that it was created, renamed, deleted and destroyed, with the authorship of each, and who could reach it. The activity of a deleted notebook answers exactly that and nothing more. A notebook still alive is untouched: removing a folder or a note changes nothing about its trail. It is **not retroactive** — a notebook deleted before this version keeps the trail it has — and an export is what makes the history of a notebook survive on purpose (RN-AUD-001, RN-AUD-010, RN-AUD-011). (#149)

- **Importing a notebook is a page that shows what it will create, lets it be chosen, and says how far it got.** It was one button: the file was read only by the server, after the upload, so the first thing anybody learned about its contents was whether it had worked; the notebook was named after the FILE, so exporting a notebook and importing it back — the most natural test of a backup — hit a name already taken and showed the refusal as raw text; it was all or nothing; and a notebook large enough could not be imported at all, because the whole import ran inside one request that stops at 29 seconds. Now the browser opens the archive on the spot and validates it against the same format the server reads, the name comes from the document and is checked against your notebooks as you type it, and what to import is chosen — everything, only the structure (the Guidance, the folders and their Templates, and not one note), or items picked in a tree where a checkbox takes the whole branch and a folder shows as mixed. A folder nothing selected but holding something selected is written as a path, so a note never arrives without its folder; two notes of one name in one folder are refused only when both are chosen; the summary states what will be created and how many links will point at notes left out. The import itself is a job with a progress you can leave and come back to, cancelling takes the notebook back down and frees its name, and every refusal reads in `en_US` and `pt_BR` instead of arriving as raw text (RN-PRT-012, RN-PRT-015, RN-PRT-017, RN-PRT-018). (#143)

- **An export is a job that finishes, kept in Transfers until you delete it.** The whole export used to run inside the request behind the button, and the function serving that request stops at 29 seconds, so a notebook large enough could not be exported at all — and what it produced was reachable for fifteen minutes, listed nowhere, and destroyed by the bucket the next day. An export is now started by the interface and built by a worker, reporting how many notes it has read; the download starts by itself when it ends while you are still on the page that asked for it, and **Transfers**, an icon beside the user menu in the place a browser puts its downloads, is where it is followed, downloaded again through a link minted at that moment, and deleted — which destroys its bytes. A kept export counts towards the storage of the plan, and an export with no room left is refused before the work rather than after it. **An export survives the deletion of its notebook**, which makes it the one way back from a deletion by mistake, and deleting a notebook through the connector now says how many exports of it stay (RN-PRT-019, RN-PRT-020, RN-PRT-021, RN-SUB-021). (#145)

- **The skill that teaches writing a note says how to cite a source.** A source with an address of its own — a file at a commit, a URL with an anchor, an article of a norm — is cited with a link where it is used, with the passage that matters quoted in the note; a source earns a note of its own when it has no address, such as the output of a command or an interview, or when many notes cite it; and a passage many notes cite is embedded rather than copied. Each case comes with an example. A notebook written in staging had given every excerpt a note of its own, and 693 of its 811 notes were evidence a link would have carried. (#133)

- **The skill that designs a notebook teaches what made six agents write alike, and what left the notebook unfinished.** A folder description now has three parts — the question its notes answer, the content they typically carry, and where what looks like it belongs goes instead — with an example, because agents that never talked to each other wrote alike in folders described that way. A subfolder is created when its first note arrives, since 35 of 55 subfolders created up front were still empty when the writers stopped. A name says what the note holds and the folder what kind it is, so no name carries a kind prefix; the records that multiply are numbered with `next_number`, with the description in the text of the link; a kind of note that multiplies is weighed before it is chosen; and the line of a map is added with the note it points at, rather than left for an end that never came. The checklist before saying a notebook is done checks each of them. (#132)

- **`list_notes` answers an index an agent can hold, in pages.** It answered every note at once, each with its size, its instant and a whole authorship: a notebook of 811 notes answered 465 KB, and the client refused to show it. Each note now comes as its identifier, name, folder and position, in pages of 100 (up to 500) inside `{ notes, nextCursor }`, and a page continues from the note it ended on, so a note written between two pages is neither read twice nor skipped. The interface keeps its full listing (RN-AGT-031). (#130)

- **A folder that keeps its notes in subfolders no longer reads as empty.** The tree and the outline of the web show the notes of the whole subtree, with the split in the tooltip — "0 here, 26 in subfolders" — and a subtree with no note still shows nothing. The Notebook Context, which an agent reads without a tooltip, prints both: `(0 notes here, 26 in subfolders)` for a folder with subfolders, and `(N notes)` for one without (RN-AGT-035). (#136)

- **A folder holds one note of each name, and a retry finds the note it made.** Creating a note whose name its folder already holds is refused with `ALREADY_EXISTS` and the identifier of the note that holds it, and writes nothing; so are renaming a note to that name and moving a note into that folder. Another folder may hold a note of the same name, and the folder is what tells the two apart for whoever reads — a link still reaches every note of a name, across the notebook. Deleting a note frees its name at once, a note with no name reserves nothing, and names compare trimmed, NFC and case-exact. A `create_note` retried after its answer was lost is refused naming the note the first call wrote, and the answer tells the agent to read it and change it with `update_note`, or to choose another name or folder. An import carrying two notes of one name in one folder is refused whole, before its first write. Six agents writing one notebook in staging had left three such twins, each minutes after the first, in folders too large to list first (RN-KNW-037, RN-KNW-042, RN-AGT-024, RN-AGT-030). (#129)

- **`note_history` stops answering about a note somebody deleted.** The trail keeps every entry of it, appended and immutable, and the product stops serving them: what they point at was destroyed, so a history that still listed them would be an index of content nobody can fetch. `read_note` with `asOf` answers the same way. The history of a note still in use is untouched, superseded revisions included (RN-AUD-010). (#140)

- **What is deleted is destroyed, and the subscription stops paying for it.** Nothing in the product used to destroy a byte: a deleted note, a removed folder and a deleted notebook all stayed in the store forever. Now a queue fed by the deletion itself feeds a worker that walks what the deletion invalidated and destroys it — every revision of the content in the store, the items in the table and the projections in the search, the graph and the facets. It runs after a delay, so a note written into a folder at the instant of its removal is purged with it; it is delivered at least once and a second pass changes nothing; and a subtree larger than one run continues in a message of its own. The storage of the subscription is freed when the purge completes, not at the click, and each unit is counted once. The audit trail keeps every event of what was purged, the purge included, and from then on their content references point at content that no longer exists: the history of a note somebody deleted stops being readable, and that of a note still in use does not. Exactly one principal in the system may destroy a revision, and it reaches the store through a port of its own (RN-KNW-047, RN-AUD-010; RN-AUD-006 removed). (#140)

- **Deleting is definitive, and what is under a deleted thing goes with it.** A note, a folder, a notebook: each leaves every listing, the search and every context the instant it is deleted, and nothing brings it back. There is no trash in the product, and a notebook that wants one declares it in its Guidance — a folder, and a rule saying to move a note there instead of deleting it, which an agent follows. Deleting is one write on the thing deleted: everything under it becomes invalid in the same instant without being written, so removing a folder is one write whatever the subtree holds, the ceiling of 200 notes on a `CASCADE` is gone with the loop it protected, and a note written into a folder at the instant of its removal is invalid the moment it lands, where it used to survive live in a folder nothing showed. The name of a deleted notebook is free at once (RN-KNW-029, RN-KNW-033, RN-KNW-046; RN-KNW-040 and RN-KNW-041 removed). (#140)

- **A Template belongs to its folder and a Guidance to its notebook, instead of being a field of it.** Each is an object of its own now, with its own address, and writing one is a write of that object: it no longer locks the whole notebook. Writing the Template of one folder used to conflict with renaming another folder, and two agents writing the Templates of two folders conflicted with each other; twenty Templates written at once while a folder is renamed now all succeed. A folder still holds at most one Template and a notebook at most one Guidance, guaranteed by the address of each rather than by a check, so two first writes racing for one folder leave exactly one Template and the other is told it lost (RN-KNW-044). (#139)

- **A note is named by the `name:` of its frontmatter, and no longer given by whoever writes it.** `create_note` takes a folder and a body, and nothing else. Nothing but `name:` names a note: not a heading, not a first line, not a file name. The same function reads it on the write and on the resolution of a link, so the two can never disagree about what a note is called. A note is renamed by editing its `name:`, and the route that renamed one is gone (RN-KNW-035, RN-KNW-038, RN-KNW-039). (#96, #109)
- **Nothing in a notebook is unique any more, and `create_note` always creates.** Two notes may carry the same name, in one folder or in two, and nothing refuses the second one. The tool declares itself as **not** idempotent: a call that fails on the way back may have written, so read the folder before calling it again, or you get two notes where you meant one. Moving a note between notebooks carries no conflict policy, deleting one releases nothing and restoring one requires nothing to be free (RN-KNW-037, RN-AGT-024; RN-KNW-020, RN-KNW-021, RN-KNW-022, RN-KNW-030 and RN-AGT-004 removed). (#96)
- **A note may have no name, and every surface says so instead of showing an empty line.** A note whose frontmatter states no `name:`, or whose name carries one of `#`, `[`, `]` and `|` — the four delimiters of the form that addresses a note — has no name. It is written all the same, it renders and it is searchable: refusing the write is how an import loses a notebook (RN-KNW-036). (#96, #109)
- **The frontmatter reserves three names, and the notebook is told which they are.** `name`, `aliases` and `tags`: what a note is called, the other spellings a link may find it by, and its subjects. A name is reserved when the product decides something with it, or when every notebook needs the same one. The Notebook Context now carries a `## Reserved attributes` section saying which they are, and that reserving a name is a guarantee and not a prohibition — `etiquetas:` keeps working and keeps being indexed. **`author`, `co-author`, `created` and `updated` are ordinary attributes**, which a notebook writes or not as its Guidance says: who wrote a note and when is answered by its history, which records every write with the person and the connector, and the product teaches no value for them. It had taught one — `author` as the person who authorized the connection — and an agent following it wrote the e-mail of the connected account into notes other people produced (RN-AGT-025, RN-DSC-030). (#105, #121)
- **The connector teaches how a note is named once, and says what a heading is for.** That `name:` names a note was stated as a prohibition in eight places — `whoami`, three tool descriptions, both skills, two rows of the notation table and the Notebook Context — and none of them said what a heading does, so agents stopped writing level-1 headings and copied the prohibition into the Guidances they wrote, where a notebook states its own conventions. It is now said once and positively: the name is the `name:` of the frontmatter, the title the page shows and what every link looks for, and the headings of the body are its structure, starting at `#`. The edge cases stay in the specification and in the notice a note with no name is answered with. (#122)
- **The skill that designs a notebook teaches how a good one is built, instead of asking for samples.** `design-notebook` opened by asking the person for three things they wanted to keep, and it stopped a person who only wanted the notebook, while saying nothing about the practices a notebook is made of. It now teaches them, each as this product implements it: short notes with one concept each, linked, with a pending link as the list of what is still to write; folders and subfolders whose descriptions say where a note goes, in an order that is data rather than a number in the name; properties and tags, lists in brackets, prose in the body, `#subject` left for the frontmatter; maps of content, and where they live; a template for every folder that receives notes, subfolders included; and the formatting that fits the material — a table for a comparison, a callout for a rule, a diagram for a flow, a formula, an embed instead of a copy — with the syntax of each form read from the specification. The agent proposes a structure and confirms it with the person before creating, and `create_notebook`, `whoami` and `list_notebooks` ask for that confirmation where they asked for samples (RN-AGT-028). (#127)
- **`name` never becomes an attribute**, whatever the shape of its value: no facet, no filter, no statistic. It names the note, and a note is not a category of itself. **`title` is an ordinary attribute**, classified like any other, and it names nothing (RN-DSC-050). (#105, #109)
- **The properties of a note are drawn in a declared order**: the reserved keys first, in the order the specification declares them, then the vocabulary of the notebook in the order the note wrote it. Only a reserved key is labelled in the language of the interface; `author`, `created` and every other key a notebook writes are drawn under the key as written (RN-DSC-051). (#105, #121)
- **The reserved vocabulary is read from the specification and typed nowhere.** It existed in three copies — the facet extractor, the property panel and the locale files — and each could drift from the specification and from the other two. It is now derived from the notations the specification files under §6.4, so a change that reserves one more name reserves it here in the same commit. (#105)

- **The three messages the pool sends leave from the product, dressed in the brand and in the language of the account.** The invitation with its temporary password, the confirmation code and the code to set a new password came from `no-reply@verificationemail.com`, in plain text and in one language whatever the account spoke, capped at 50 a day. They now leave from `no-reply@memorysmith.app` — `no-reply@stg.memorysmith.app` in staging — through SES, as HTML with the signature of the brand, in `pt_BR` or `en_US`: the language given when the account was created, and after that the one the person last chose in the interface, which is now recorded on the account. The credential stands alone on its own line, larger and centred, and nothing follows it, because a full stop sitting against a password reads as part of it. Every message says how long its credential lasts — 7 days for the temporary password, 24 hours for a confirmation code, 1 hour for the code of a new password — and the invitation says where to sign in and that the first sign-in asks for a password of one's own. `onboard` takes `--locale` (RN-ACC-017, RN-ACC-018). (#57, #106)

- **The product implements the MemorySmith Markdown Specification at v0.6.0**, which is also its new name: `markdown-profile` is `markdown-spec`, `profile.json` is `spec.json`, and the suite it publishes now **builds a notebook** — twelve cases that say what each target becomes, its kind and how many edges it produces. Those cannot be run against a reader alone, so the resolver runs them. (#97)
- **A link resolves against the name of a note**, compared case-exact after Unicode NFC and folded in no other way. `[[Lei 14133]]` no longer finds `Lei 14.133`: it is a pending link, which is visible, where the old collision was silent — the slug it used to compare was not injective, and `Ação` and `Acao` were one key, as was every name in a non-Latin script. A wikilink target is **literal**: no decoding, no extension removed, no path discarded. The three tolerances belong to the Markdown form alone, in the order the specification fixes (RN-DSC-041, RN-DSC-043). (#97)
- **One link into two notes with one name is two edges**, and the backlink on both is honest about it: never the first one, because there is no order to appeal to (RN-DSC-042). (#97)
- **An alias resolves a target that no name matched**, and only that. The frontmatter may say what a note is called and may not redirect a link that has already found a note. The cost is named: **resolution is no longer monotonic** — writing a note takes an edge away from whoever was holding it by alias, in a third note nobody touched, and deleting it gives it back (RN-DSC-052, RN-DSC-053, RN-DSC-032 revised). (#97)
- **An attachment is addressed by its name and is never an edge.** This product stores none, so a reference to one is reported the way a pending link is — distinctly, saying what it is — instead of being drawn as a link to a note nobody will ever write (RN-DSC-044, RN-DSC-049). (#100)
- **An image carries its dimensions in its alt text.** `![Engelbart|100x145](…)` is drawn at that size with `Engelbart` as the description, and neither the pipe nor the digits reach the page as text. A value that is neither `100` nor `100x145` is not a dimension and stays part of the description, because deleting what an author wrote into an accessibility label is the worse failure (RN-DSC-048). (#100)

- **The interface addresses a note by its identifier, and a name addresses a link target.** A URL is an address and names one note; a wikilink is a name, and a name may match several notes, so the two are kept apart (RN-DSC-045). (#98, #107)
- **A wikilink that answers with none or with several notes has an address of its own**, under `/notebooks/:notebookId/links/<target>`: the choice lists every candidate with the folder it lives in and says whether they match by name or by alias — because an edge held by an alias is one somebody takes back the day they write a note under that name (RN-DSC-046, RN-DSC-056). (#98)
- **The note page draws the name of the note in its frame, always**, and every heading of the body is an ordinary heading. When the frontmatter states no name, the frame says so (RN-DSC-054). (#98, #109)

- **The graph draws a note and never a name.** A node is identified by the note, so two notes carrying one name are two nodes — both labelled with it, told apart by the folder written beside the label — and a link into that name is two edges leaving one note. It used to key a node by the slug, which under one name would have drawn one node and silently lost the other. Clicking a node opens that note directly and never the choice, because the graph already knows which one it drew (RN-DSC-047). (#99)

- **A notebook leaves as one document.** The export is a single open JSON file, zipped, with the extension `.notebook`: the notebook, its Guidance, every folder with its parent, position, description and Template, and every note with its folder, its position, its dates and its **body byte for byte**. It used to be a tree of `.md` files, which was a one-way door — the identity of a note, its fractional position, the description of a folder, the Guidance, the Template and the dates were all dropped at it, which is why nothing could be brought back. **Nothing derived is stored**: no name, no slug, no numeric prefix, and no link destination is rewritten (RN-PRT-009, RN-PRT-010, RN-PRT-011). (#101)

- **A `.notebook` file becomes a notebook: the import.** The product reads back what it hands over — the other half of the door, and the half that makes a backup something somebody has tested. An import **always creates a new notebook** (no merge, no conflict, nothing to overwrite), **mints every identifier** rather than restoring the ones the document carries, and is **refused whole before the first write** when the file is not an archive, the document does not match the format, the version is one this build does not read or the plan has no room. The file is uploaded to a short-lived address under the subscription and discarded once the import ends. Every write carries the authorship of whoever imported (RN-PRT-012, RN-PRT-013, RN-PRT-014, RN-PRT-015). (#104)

- **The Markdown specification lives in this repository, in `docs/markdown-spec/`, and follows the version of the product.** It was a repository of its own, pinned here by a git tag, so changing a notation took a release there and a pin bump here before the first line of implementation. It came in with its history, and a notation now changes in the same commit as the readers that implement it. What it says did not change, and every conformance case runs exactly as before. What changed is that nothing carries a second version: the skill names the specification and an address inside this repository without citing a version of its own, and a `.notebook` document no longer declares one, because the version of the notation its bodies are written in is the version of the product that wrote it (RN-AGT-022, RN-AGT-023, RN-PRT-011). (#110)

- **Vault is now Notebook, everywhere the product says it, and Caderno in `pt_BR`.** "Vault" is the word Obsidian made its own for a folder of Markdown notes, and keeping it said that a notebook here is an Obsidian vault served remotely — which stopped being true once the notation became a specification of this product. The tools are `create_notebook`, `list_notebooks`, `delete_notebook` and `get_notebook_context`, and every argument and field that said `vaultId` says `notebookId`; what an agent reads before writing is the **Notebook Context**; the per-unit ceiling of a role is the **Notebook Role Limit**. The routes of the API, the addresses of the interface, the domain events and the export follow: a notebook leaves as a `.notebook` file and comes back from one. The description of `create_notebook` says it creates a notebook of Markdown notes, and not a Jupyter one. **A connector that remembered the tool names of 0.5.7 finds none of them**, which is why it happens now, in the version that already breaks every address and the export, and before any connector is built against 0.6.0. A note is still a Note, and where "vault" names the concept of another tool — the vault editors — it stays. (#111, #108)

- **A heading is only content, and a note is named by `name:` alone.** This cycle had named a note in a chain — `title:` of the frontmatter, and the first level-1 heading when there was none — which made a heading two things at once: editing the opening line of a text renamed the note in silence and moved every edge that pointed at it, and a note opening with a section heading answered to a name nobody chose as a name. Now `name:` is the one thing that names a note, `title:` is an ordinary attribute that may become a facet, and `name` never does. `title` became `name` wherever it meant what a note is called — the API and its DTOs, the domain events, the answers of the MCP tools, the search field `name:`, the graph, the listings and the interface — and `whoami`, the skills, the Notebook Context and the descriptions of `create_note` and `update_note` teach it. The specification says it in §5.3, §6.4 and §6.5, and its suite carries the cases of the name. **The migration of 0.5.7 is gone with the chain**: it wrote `title:` into every note, which would now leave every note without a name, and the environment it was written for is destroyed before 0.6.0 goes up (RN-KNW-035 to RN-KNW-039, RN-DSC-050, RN-DSC-051, RN-DSC-054). (#109)

- **Every address of the interface is an identifier, and nothing else.** A notebook is `/notebooks/<notebookId>`, a folder `/notebooks/<notebookId>/folders/<folderId>` and a note `/notebooks/<notebookId>/notes/<noteId>`: no slug, no label, no folder trail, and a note is not nested under its folder. Renaming a notebook, a folder or a note, and moving a note, changes no address, so a link somebody saved lands where it was saved. **Every address saved before 0.6.0 answers not-found** rather than being redirected, because resolving one would mean reading a name out of an address; where the reading stopped in each notebook is now kept by identifier, and what a browser remembers from 0.5.7 is dropped. An identifier reads in either case and is written in lower case, and opening a notebook no longer lists every notebook first to find the one its address named (RN-DSC-045, RN-DSC-055, RN-DSC-057). (#107)
- **The title of the tab names what is open**: the note, the folder, the link target or the page of the notebook, then the notebook, then the product — `Lei 14.133 · Procurement · MemorySmith`. It said `MemorySmith` on every page, so two tabs, two entries of the history and two bookmarks could not be told apart, and with no name in the address it is where a person reads which is which. A note with no name is titled with the label every other surface gives it (RN-DSC-058). (#107)

- **Onboarding an account is a command of the repository, in TypeScript.** `pnpm -C memorysmith-infra onboard --environment staging` does what `onboard.ps1` did, with credentials of the account of the environment: it creates the account in Cognito, makes the first account of an empty pool a platform admin, asks for the subscription, sets its quota and status through the administrative override and hands the account over with a provisional password nobody running it ever learns. The account starts with no notebook. Calls throttled or answered 5xx are asked again, and an answer is never repeated. (#108)

On the web the Guidance panel, the folder page and the page of Templates offer it to whoever may write, and it asks first, in the page rather than in a browser dialog, because what a person needs in order to answer is the sentence saying what survives — which does not fit in a dialog title. What a deleted one occupied leaves the storage count of the subscription, and no byte is destroyed: the content stays in the store, as it does for a deleted note (RN-KNW-045). (#139)

A note written a moment ago anchors the next one, although the listing of its folder converges only after the write. An anchor that is not a sibling is refused with the siblings it could go after, through the connector and the API alike, where it used to put the item last in silence, and the two reorder routes answer the folder and the note as the write left them instead of nothing (RN-AGT-029, RN-AGT-014). (#124)

- **Before a release, an agent that knows nothing but the connector is asked to use the product, and the notebooks it leaves are judged.** `pnpm -C memorysmith-infra agent-eval --environment staging` plays a catalogue of cases — a notebook designed with material at hand and one asked for vaguely, a second agent writing into the notebook the first designed, and inline tags converted only as far as the person accepts — each in an account of its own, connected through the whole OAuth flow, three runs each in Sonnet and in Haiku. The mechanical checks of every run go into a scorecard posted on the issue of the cycle, beside the judgement read against the rubric of each case, and nothing blocks the merge. (#112)

A journey has an agent write a note by the Guidance and the Template through the connector, the owner tick its box on the web, and the history name both of them. A page added to the router without a case fails the Quality stage. (#108)

Then, through the official MCP SDK, it checks what the connector answers without a token, that the handshake and `whoami` say which environment this is (RN-AGT-026), and every tool of the catalog, one case each, against the live `tools/list`: a tool added without a case fails the suite. Which routes there are is `routes.json`, a manifest a test of the core keeps equal to its app, so a route added without a case fails the Quality stage before anything is deployed. A projection is awaited by polling up to 30 s, never by sleeping, and the latency of every route goes into a report kept 30 days in a private bucket of the account, whether the suite passed or not. The interface shows a banner that cannot be dismissed, puts `[staging]` before the title of every tab, and keeps the version in the user menu. (#108)

What bounds a notebook now is the storage quota of its subscription; the ceiling of 200 folders stays, because it bounds the Notebook Context an agent reads (RN-KNW-010). (#134)

What they stood on is gone with them — deleting is definitive (RN-KNW-029, RN-KNW-033) — and the two events, `NotebookRestored` and `NoteRestored`, stay in the contract marked as retired, so a trail already written stays parseable. (#120)

- **The workflow of GitHub Actions, `docker-compose.yml` and `.dockerignore` are gone.** The quality checks and the tests run inside both pipelines, as the same `pnpm` scripts a workstation runs, and the adapter tests run in the staging pipeline, after the deploy, against the real DynamoDB and S3 of the environment, every case under a subscription of its own. The promise that made RN-PRT-001 worth making is kept — the format is open and specified, every body is plain-text Markdown, nothing is encoded or obfuscated — and what is spent is unzipping the archive straight into a vault editor. Turning a `.notebook` document back into a tree of `.md` files is a conversion this product does not perform (RN-PRT-001, RN-PRT-002, RN-PRT-003 and RN-PRT-005 removed). (#101)

The route `GET /notebooks/:v/notes/by-slug/:slug` is gone with it. A note is addressed by its identifier and named by the `name:` it states. The slug of a **notebook** and of a **folder** is untouched (RN-KNW-032, RN-KNW-002). (#96)

### Fixed

- **What a transfer carries is chosen the same way on both sides, and the tree shows what is under what.** An export carried everything or nothing; an import chose, from a list where a note sat one step from its folder with no guide, no twisty and no count, so a folder of twelve notes read as thirteen rows of one kind. Both sides now offer **the whole notebook** — the Guidance, the Template of each folder, every note and the history — in one click, and **choosing items**, which asks in two tabs: the **context** of the notebook, where the Guidance, the history and the Template of each folder are ticked in a tree of folders from the root, and the **notes**, in a tree of folders and the notes in them. Each level is indented and carries a line down its side, a folder says how much it holds, and a Template carries the folder it belongs to — without which the design of a notebook could be chosen and would arrive with nowhere to write it. An export chooses from the structure the API answers, since it has no document yet, and what it chose travels with the job: the archive carries only that (RN-PRT-017, RN-PRT-024). (#156)

- **A transfer says what it is, and an import stops saying it weighs nothing.** A row of Transfers carried the name of a notebook and a size, so an export and an import of the same notebook read the same — and the size of an import is always zero, because an import keeps nothing: the file you gave it is discarded the moment it ends. `0 B` beside an export of 1 MB reads as a job that did nothing, and it had written a whole notebook. A row now says what it is in one line — the notebook an export came from and the file it saves as, the file an import came from and the notebook it created — and what it ended with: the bytes an export keeps, which count towards your plan, and the notes an import wrote. An import that brought a design alone says so instead of counting zero. The file you chose travels with the job, so Transfers can name it weeks later (RN-PRT-014, RN-SUB-021). (#155)

- **The actions of the product look like actions.** There was no button: `.chip` is a label — the size of a piece of metadata beside a title, blue on blue — and every action had borrowed it, so the one that commits and the one that cancels were the same tag, and a screen whose every control is blue spent on buttons the share the brand gives the blue as structure. There is a button now, with the three intents the product has: the one that commits, the quiet one beside it, and the one that destroys, which says so before it is pressed and fills only under the hand. Every action adopted it — starting an export, importing, confirming, downloading, deleting — and a chip is a label again. A control is also a target a thumb reaches, which one the size of a tag was not. (#157)

- **The window holds the whole application, and the banner of the environment stops covering the menu.** The banner outside production was fixed over the page, so it was drawn over the end of the folder tree; to make room for it the body carried a padding of exactly its height, which made the document taller than the window. The scrollbar that came out of it moved the layout and no content: the sidebar and the middle each scroll on their own. The application is now three rows of one window — the header, the page and the banner — the banner covers nothing, and in production its row has no height, because there is nothing to put in it. What scrolls is what has content. (#158)

- **A transfer is decided in one dialog and followed in one place.** Exporting opened a modal and importing was a page of its own, so the two halves of one job were asked for in two shapes: one commanded by a filled blue button and the other by a white one, as if one mattered more. A transfer is now asked for in the same dialog whichever way it goes — large enough to read a tree of sixty-eight folders through, with the question fixed at the top, the actions fixed at the bottom and one scroll between them — and starting it closes the dialog, because what happens next is Transfers, where the job is already watched, saved and deleted. The two ways in are peers, the panel gets out of the way when the dialog opens, and a finished import carries the way into the notebook it wrote. **Nothing downloads by itself**: an export used to save itself the moment it was ready, wherever the person had moved to, which was a third way to get a file beside the two buttons that ask for one. A row of the chooser whose Guidance, Template or history does not exist says so and cannot be ticked, instead of being absent with nothing said, and a transfer names its notebook once with its file on the line under it. (#160)

- **Every notebook written before this cycle has its Guidance and its Templates back.** This cycle gave the Guidance and the Template a life of their own — each an object with an address, instead of a field of the thing it belonged to — and nothing carried over what was already written. So a notebook written before it answered "no Guidance" and "no Template" on every folder, for ever, while the content sat in the store and its own history recorded every write of it: on staging, one notebook had a Guidance and 57 Templates written and showed neither. A maintenance job now moves them, reporting what it will do before it does it and writing nothing the second time it runs. Not one byte of content is read or written: what moves is where the product looks for it. It also ends the silence downstream — an export was carrying `null` where the design should be, so an import had nothing to write. (#159)

- **A note written into a folder created a moment earlier is no longer refused.** Every write loads the notebook it is about to change, to authorize it and to check it against — a folder exists, a name is free, a ceiling allows it — and that read did not ask for the newest state. A store that had not settled answered the notebook **without the folder written a moment ago**, and the write was refused with a `404` naming that folder. It is the sequence an agent performs most, `create_folder` and then `create_note` in it, and it worked only because the window is usually milliseconds. A write now reads the newest state; a listing and a page still read what has settled, which is what eventual consistency is for and costs half. (#154)

- **Cancelling an import leaves nothing, even when the cancel lands in its last instant.** A cancel is a write on the record and the worker is what acts on it, between notes: it takes the notebook back down and stops. The one it missed was the cancel that arrived after the last note was written — the job saw it, stopped, and left the notebook standing, with the name it had taken, under a transfer that said it had been cancelled. What the job discovers too late it now undoes (RN-PRT-014, RN-KNW-033). (#153)

- **A deletion in the search leaves nothing behind, even when what it deletes was written a moment earlier.** Every walk that decides which items a deletion takes — the parts of a large note, the sweep of a notebook, the edges and the pending targets of a note — read without asking for the newest state, so a table that had not caught up answered fewer items than existed. What it did not answer was never deleted, and nothing walks those again: what named them is gone. They stayed stored for ever, which is the one thing a deletion promises it does not do. The walks of a deletion now read the newest state, like the purge already did; the reads that answer a person are untouched (RN-DSC-013, RN-KNW-047). (#152)

- **An import that wrote the whole notebook says so, instead of reporting a failure over the file it came from.** The last thing an import does is discard the upload it was given, and that delete was the one permission the worker never received when the import moved into it — so the job ended on a sentence of the cloud provider, cut mid-word at 200 characters, naming a notebook that had in fact been created and that its record pointed at nowhere. The permission travels with the work now, still reaching the uploads of an import and nothing else. Beyond that, **a cleanup that fails no longer decides the import**: the upload is what the rule of the bucket expires, the notebook is what somebody asked for, and a transfer that fails for a reason nobody foresaw writes the whole of it where the log of the worker keeps it (RN-PRT-014, RN-PRT-018). (#148)

- **An export and an import finish, instead of staying on `running` for ever.** The worker that runs them writes as the person who asked, so it reads the role they hold — and the stack never named the table where that is read, nor let it write the notebook an import creates. A handler reads its environment when it loads, so the function failed before its first line and every job sat unanswered. Both halves are checked now: a case reads what each handler requires and what its stack gives it, and fails until the two agree. (#143, #145)

- **The choice a link to several notes opens is a dialog over the page, and no longer a menu inside a table.** It was drawn in place, anchored to the link and positioned inside whatever held it — and every table of a note scrolls on its own, so a link written in a table cell opened its choice inside the scroll box of the table: clipped by it, with a scrollbar of its own, in a box too small to say what it had to say. It now opens over the page, saying that the link reaches more than one note and what tells them apart — the folder trail leads each option when a name matched, since every option carries that name, and the name leads when an alias did. At phone width it is a sheet from the bottom, with targets a thumb reaches and trails that wrap. `Esc`, the backdrop, ✕ and Cancel all close it, and the focus goes back to the link. A click that takes a moment to resolve opens on placeholder rows instead of looking ignored, and an alias that answers with one note still goes straight there. The page at the address of a link target renders the same explanation and the same options, from one component (RN-DSC-046). (#144)

- **A deleted notebook stops leaving items of itself in the search for ever.** Deleting a notebook walked its notes one by one, deleting each as if it were a deletion of its own — which returned the links pointing at each note to pending, so a link between two notes of that notebook WROTE a pending item as the first one went, and the note that wrote it was removed right after. On top of that, removing a note never took the pending targets the note itself had written, nor the marks on the edges one of its aliases answered for. None of it was visible to anybody — a pending link whose source is gone shows in no listing and in no backlink — and all of it stayed stored, which is the one thing a deletion promises it does not do. Each projection now wipes what it holds of a deleted notebook in one sweep, removing a note takes everything that names it, and the marker that stops a late event from resurrecting a note is kept for thirty days instead of for ever — longer than any delivery it defends against (RN-KNW-047, RN-DSC-013). (#147)

- **A deleted note stops answering about itself at once, and only through the notebook that holds it.** Between a deletion and the purge that follows it a minute later, the two reads of the audit trail went on serving a note every other surface already answered as missing: `note_history` listed its whole timeline and `read_note` with `asOf` handed back its body. They also took the note and nothing else, so the notebook named in the call was thrown away — a note answered the same through a notebook of another subject and through an identifier that never existed. Both reads now travel under the notebook, `/audit/notebooks/:v/notes/:n/…`, and check the chain before answering: the note, the folder it lives in and the notebook above it, whether or not the purge has run. The history of a note in use is untouched, the empty history of a note whose first event has not landed yet is still an empty history, and the activity of a notebook keeps answering after it is deleted — that is the one read of the trail a deletion does not take away (RN-KNW-046, RN-AUD-010). (#146)

- **A `.notebook` file can be imported through the interface, which no file ever had been.** The import uploads the file straight to the content bucket, and the bucket let the site do nothing there but read: the browser asked whether it might upload, was refused before a byte left, and the button showed the raw words of the browser, `Failed to fetch`. The request never reached the API, so not one of the refusals the import declares ever ran. Nothing caught it because every test uploads from Node, where nobody asks: a functional case now imports a notebook through a browser, which is what would have. The site may upload to the address the API signs for it, which is one key for a few minutes — the verb is what widened, never the reach (RN-PRT-012). (#142)

- **A note larger than about 200 KB is found by the search.** Its searchable portrait was one database item carrying the body twice, and an item holds 400 KB: a large note never reached the search, and one that grew past the limit kept answering from the text it had before. The portrait is now split into parts, so a note of up to 1 MB is found by a word written at its very end, a note that grows answers its new text, and deleting it removes every part; a portrait caught halfway through a rewrite is never answered as if it were whole (RN-KNW-025, RN-DSC-027). (#135)

- **A link to a name several notes carry offers the choice where it is clicked.** Every reading surface drew it as a dead pending link, and the page with the choice was reached by nothing. The note, the folder, the Guidance and the Templates now resolve a link one way: one note is a link, several open a menu in place, each option written as its folder trail and its name, and a name no note carries is drawn pending and can still be clicked — the click asks the aliases, opens the note one of them answers, and otherwise says nobody carries the name yet. The menu is reachable with the arrow keys, closes with `Esc` or a click outside, and the link keeps a real address for a new tab (RN-DSC-046, RN-DSC-060). (#138)

- **A moved note is still found by its words, and keeps its links and its facets.** The move carried no content, so the projections read it as an empty note: moving a note to another folder or notebook took it out of the search and its links out of the graph until it was written again. The move now carries the content, and every note event carries the version of the note, so an older event delivered late — or the same event delivered twice — leaves the search, the graph and the facets on the newest note; a failed projection goes back to the queue alone instead of with the nine others of its batch (RN-DSC-012, RN-DSC-023). (#141)

- **An agent can replace a Template that already exists.** `get_template` answered the Template as text and dropped the revision the next `set_template` has to state, so replacing a Template through the connector had no path that succeeded: the only way was to send a revision that would conflict on purpose and read the current one out of the refusal. It now answers the content and the revision, as `get_guidance` does, and `set_guidance` and `set_template` answer the revision each write produced, so a second write needs no read in between (RN-AGT-016). (#123)
- **Sending the same content again writes nothing, and the next write based on its answer goes through.** Re-sending the body a note, a Guidance or a Template already holds produced no event and moved no pointer, as promised, but it still stored a new version of the whole body in S3 that nothing referenced and nothing may ever remove. For a Guidance and a Template it also answered the revision of that version, which the pointer never took, so a second write based on it was refused as a conflict. The body is now compared with the content in force before anything reaches the store, and the answer is the revision in force (RN-KNW-028). (#125)
- **A note written beside another that shares a value of its frontmatter reaches the search, the graph and the facets in seconds, and no longer six minutes later.** Two notes of one notebook with a value in common — the same `maturity`, the same tag — move the same counter, and DynamoDB cancels a transaction over an item another transaction holds in flight. The projector took that ordinary answer as a failure and sent its whole batch back to the queue, so every note in the batch waited out the six minutes the queue hides a message for before being projected again; the alarm on the errors of the projector showed it on staging. A cancelled transaction is now tried again in place, against the portrait of the note read afresh, and that portrait is written only over the revision it was read at, so two projections of one note never both count the same change. (#108)
- **The health of a notebook reports its pending links once, and no longer calls them broken.** It answered the links to a name no note carries yet twice, as `pendingLinks` and again as `brokenLinks`, so a reader adding the two counted every one twice. Nothing in a notebook is ever broken: such a link is pending (RN-DSC-004), and deleting a note returns the links that pointed at it to pending (RN-DSC-005). `brokenLinks` is gone from the answer. (#117)
- **The history no longer loses an entry when the table asks it to slow down.** The audit trail writes events in batches, and under load DynamoDB answers a batch as written while handing back the entries it did not write; those were ignored, which is a hole in the one record that exists to have none. They are offered again now, and a batch still unwritten fails, so its events are delivered again and written once. (#108)
- **Every write reaches the history, the search, the graph and the counters, however many are written at once.** The relay that publishes the events of a notebook sent each batch of the stream to the event bus in a single call, and the bus takes at most ten events a call: a batch of more — an agent writing a notebook in a burst, a notebook onboarded or imported, a folder removed with its notes — was refused whole, tried again and dropped, so its notes never reached the history, the search, the links or the counters. The alarm on the queue of dropped batches showed it on staging. The relay publishes in calls of at most ten now, and an event the bus refuses fails the batch so the stream delivers it again instead of losing it. (#108)
- **Removing a folder with `CASCADE` deletes the notes it held, instead of leaving them live and out of sight.** The folders went and their notes stayed: gone from the tree, and so from anybody reading the notebook, yet still counted against the ceiling of notes and the storage of the plan, still found by search, and restorable into a folder that no longer existed. Every note of the removed subtree is now deleted the way a note is deleted — nothing destroyed, its history readable — under the authorship of whoever removed the folder, before the folders go. A subtree holding more than 200 notes is refused before anything is written, and a deleted note whose folder is gone is not restored. Listing every note of a notebook also no longer stops at the first megabyte of the table (RN-KNW-040, RN-KNW-041). (#108)
- **An agent reading the links of a notebook is told which notes they are.** `related_notes` printed `- undefined (undefined)` for every note of the tree it walked, `backlinks` answered an empty name for a note that has one and a position it does not carry, and a search hit never named its note, neither to an agent nor in the search route, which answered flat hits where the published contract declares the note. The connector now reads every answer of Discovery as the contract types it, the search route answers the note of each hit with its name, and `read_note` and `note_history` say in their descriptions what they answer: the revision as the string to pass back, and a list of entries with the connector of each write. (#108)
- **The page of Templates opens a Template again.** Reading the Template of a folder answered its content without the revision the published contract promises, so the page failed with "Something went wrong" on opening any Template. The answer carries the revision now (RN-KNW-034). (#108)
- **Notes written at the same time into one folder are all written.** Every note write checked, inside its transaction, that its folder existed, and DynamoDB cancels a transaction when one of its items is part of another transaction in flight, a checked item included. An agent writing notes into a folder in parallel, or two people reordering the notes of one folder at once, had writes refused as conflicts: of fifty notes created at once, thirty-three were refused. The emulator the tests ran against executes transactions one at a time and could not show it; the first run against the real tables of staging did. A note write now includes nothing but the note and its event, and the folder is read before it, as the write already did. (#108)

- **A write through the connector records the connector, and no longer the person alone.** Since 0.2.0 every note an agent wrote was recorded as if the person had typed it: `note_history` answered `agentName: null`, and `whoami` printed a user identifier where it announces the connector. Cognito issues every token of the connector proxy to one app client, and nothing carried which connector had asked for it. The proxy now binds the two when it hands the token out — the code a client redeems is sealed with the connector validated at authorization, and a token request naming another `client_id` is refused — and every write records that connector: the `client_id` URL of its metadata document and its `client_name`, which `note_history` now reports beside the name. A refreshed token keeps its connector. **A connection authorized before this fix writes nothing until it is connected again**, and says so; it keeps reading, because a write recorded without its connector would stay incomplete in a trail nothing can correct (RN-AGT-001, RN-AGT-013). (#113)

Reading it would also need a third sanctioned reader of content and a real Markdown parser in the backend, against PP4, and in a survey of the 1,562 notes of the example vaults one of the three inline matches was a hex colour. To group, write `tags:`; to connect, write `[[wikilink]]` (RN-DSC-033). (#63)
- **The frontmatter vocabulary is declared, and two of the four keys now do something.** `aliases`, `tags`, `created` and `updated` are reserved by the profile, always written in en-US, and the interface may show the label translated and never the bytes — a vault kept in Portuguese still stores `created` and still answers `created:2026-09`. Reserving is declaring rather than enforcing: a reserved key whose value has the wrong shape degrades to an ordinary attribute instead of being an error, and `title` is deliberately not reserved. A facet of kind `date` now matches by **prefix**, so `created:2026`, `created:2026-09` and `created:2026-09-03` are the three granularities and `created:09` matches nothing, where substring made a fragment of the middle stand for a date. And the entries of `aliases` join the search index as other spellings of the note, answering wherever the title does and ranking as a title hit, so a vault of technical terms is found by its acronyms. They do **not** resolve wikilinks (RN-DSC-030, RN-DSC-031, RN-DSC-032). (#62)
- **Entering a vault resumes at the note you were reading.** Every visit started at the tree, and getting back to the note open in the previous session meant walking the folder structure again, every time. The last note opened is now remembered per vault, and arriving at the vault goes straight to it. It is remembered in the browser and nowhere else: which note somebody read last is a convenience of that machine, not a fact of the product, and storing it on the server would be a write on every note opened — on the hottest path of the reading surface, against the quota, carrying an authorship that reading does not have. It resumes on arrival and not on request, so the vault name in the sidebar still reaches the Vault Context, and a note that has since been deleted, renamed or moved is forgotten in silence and lands on the tree instead of on a not-found line. (#56, #72)

### Changed

### Changed

- **Signing out goes straight to the sign-in page, with no click in between.** The product had two doors into that page and they behaved differently with nothing on screen to explain why: arriving without a session handed the browser to the identity provider, while signing out stopped at a card with a button that asked for nothing, because the provider owns the credentials. The reason recorded for that asymmetry was a loop — handing the browser back to a still-warm provider session would sign the person straight in again — and it was checked against the deployed pool before being reversed: `signOut()` goes through the Cognito `/logout` endpoint, which ends the hosted session, and the handover that follows lands on a credentials form. There was no loop left to guard against. The two paths that keep the button are untouched and now pinned by tests: an account that reaches nothing, which is the one fact a person cannot discover any other way, and a sign-in that came back empty, which is the loop guard itself. (#59)
- **The product stopped declaring its own notation and started implementing a published one.** The list of what it reads used to live in `packages/contracts` as a private declaration. It is now the [MemorySmith Markdown Profile](https://github.com/memorysmithapp/markdown-profile) `0.1.0`, a specification with a version of its own, carrying the notation as prose, as data and as an executable suite. `RECOGNISED_NOTATION` is a projection of `profile.json` rather than a list beside it, the Discovery conformance test runs the **published cases** instead of a transcription of them, and the version is pinned once, in the `catalog:` of `pnpm-workspace.yaml`, so the two packages that read it cannot drift onto two versions of one specification. A specification and an implementation that keep separate copies of the same list drift apart on the first cycle, and the drift is silent — which is exactly the failure the profile exists to prevent one layer up, for the vaults (RN-AGT-022). (#61)
- **The declared notation now covers the reading surface, and each entry is proved by a test of its own kind.** The profile declares callouts, mermaid, transclusion, the visible pending link and the interactive task list under a `reading-surface` reader — behaviour this product has and nothing proved. It earned its place on its first run, the way the published suite did against the extractors: it found #71 (RN-AGT-023). (#61)
- **`get_skill` teaches the three rings and cites the version it is teaching.** The notation table gained the ring each form belongs to, and the skill now opens by naming the profile, its version and its address, with CommonMark and GFM named as the two base specifications. "Which Markdown is this" is the question underneath every other one an agent has about writing here, and it is answered with a specification rather than with a list of forms. (#61)

Those codes name lines of `docs/software-vision.md`, a document whoever reads the connector has no access to: inside a served answer the code is a symbol that does not resolve, dropped as noise or mistaken for something addressable. Both sentences already stated the whole fact without it. The traceability stays where the other ~50 occurrences are — in comments and docblocks — and a test now walks everything the connector serves, the `whoami` text, every tool title, description and schema, every skill and every declared notation, and fails on a rule code found in any of them (RN-AGT-021). (#52)

### Fixed

- **A wikilink to a title with a decimal number no longer renders as pending.** `[[Lei 14.133]]` is a real edge — the backend resolved it, the backlink exists, the graph carries the connection — and the reading surface drew it as a link to a note that does not exist yet. The slug is computed twice, once in the kernel for storage and once in the interface to turn a wikilink into a URL, and the second copy was missing two of the six steps the profile specifies: the `.` or `,` **between two digits**, which belongs to the number and not to the words around it, and the truncation at eighty characters. So the interface addressed `lei-14-133`, found nothing under it, and told the person a note they had written did not exist. It fired wherever a title carries a decimal number, which is where these vaults live: norms, articles, versions, measurements. The two implementations are now pinned not to each other but to the **published conformance cases** — nine of which fail the moment the rule drifts again, including one that was already in the suite and had never been pointed at this side of the product. (#73)
- **The task box works: the first write the web interface makes did nothing on any note.** Clicking a checkbox changed nothing on screen and wrote nothing, in every vault, whatever the role. The cause was one line: the item decided whether it was a task by reading `checked` off the node react-markdown hands a component, and version 9 hands a **hast** element, which carries no such property. Every item therefore fell through to the plain branch and reached the screen as the checkbox GFM renders by default — `disabled`, with no handler on it. The state is now read where it actually is, on the child input, our box replaces GFM's instead of sitting beside it, and the class react-markdown passes in no longer overwrites ours. Found by the reading-surface conformance test of the profile, on its first run. (#54, #71)
- **A session that can no longer be renewed ends, instead of leaving the interface loading forever.** A tab left open past the second hour stopped working and never said so: the screen sat on **Loading…**, a reload changed nothing, and signing out was the only way through. Three defects composed into that. The first silent refresh wrote `null` over the refresh token, because Cognito does not return one on a refresh and a missing field was read as a revoked credential — a two-hour fuse on a credential valid for thirty days. Nothing reacted to `UNAUTHENTICATED`, so the guard kept letting the person in on a stale token and the session was rebuilt from claims the API had just refused. And the dashboard decided with `isLoading || !data`, which sends an errored query to the loading branch and keeps it there. The credential now survives every refresh, a token that cannot authenticate ends the session in one place and returns the person to the sign-in screen with the reason, and a screen waiting on a request that has already failed says what failed (RN-SUB-022). (#53)
- **A frontmatter list with one item is classified as a list, so an attribute no longer changes kind when a second value arrives.** `tags: [contracts]` was read as an `enum` and `tags: [contracts, budget]` as a `list`, because the classification was decided by how many values an entry happened to hold rather than by the form the author wrote. The same attribute therefore had two kinds across the notes of one vault, settled by a fact about whichever note was being read, and everything downstream that reads the kind became inconsistent for a reason invisible from the note. The frontmatter reader now carries the written form out with the values, and RN-DSC-020 — which has always said the classification is by shape — is what the code obeys. The reading surface already drew a list of one as a list, and is now pinned to the same cases so the two agree by rule instead of by coincidence. (#70)

### Added

- **The canonical documentation**: `docs/software-vision.md`, `docs/architecture-guide.md`, `docs/knowledge-base.md` and `CLAUDE.md`, replacing the old `DESIGN.md`, with explicit and non-overlapping responsibilities.
- **The MCP connector authentication spike**: `svc-agent` is born as an OAuth 2.1 Resource Server and a CIMD registration proxy in front of Cognito, validated end to end on a desktop and a web client.
- **The `memorysmith-infra` project** with the three minimal stacks of the spike, and the operational deployment guide in the `README.md`, including delegating the domain to Route 53.
- **The `memorysmith-frontend` skeleton** as a reading SPA over the seed, with i18n from the first screen, the vault graph, Mermaid diagrams and the curation dashboard.
- **The seed of vaults**, three real ones translated into the export format of the product and five fictional ones with sources inside the repository.

### Changed

- **The product was renamed from MemoryVault.guru to MemorySmith.app**, with the domain registered.
- **The tenancy model was replaced by the subscription model.** `Subscription` becomes at once the business object and the isolation boundary, with every key starting from it, and the role taxonomy was rewritten to `PLATFORM_ADMIN`, `OWNER`, `EDITOR` and `VIEWER`.
- **The platform surface is separated from customer data by construction:** a platform session carries no `subscription_id` claim, so no Knowledge repository can be instantiated under it.
- **The visual identity was defined and applied**, from the brand book: the graph-brain symbol, the palette and the typography.
- **DNS and certificates became infrastructure managed as code**, with ACM certificates validated by DNS in the hosted zone.
- **MCP client registration was decided**: `svc-agent` acts as an authorisation proxy implementing CIMD in front of Cognito, which offers no automatic client registration.
- **The repository layout was defined as three top-level projects**, with infrastructure outside the backend.
- **The language policy was revised**: the documentation of the repository in pt-BR and the source code in en-US. *(Superseded in this cycle: the whole repository is now en-US, with pt_BR only in the interface.)*

### Fixed

- The sidebar tree did not reflect navigation done outside it, the header slogan was in English in the `pt_BR` locale, and the brand symbol had a background square in dark mode.

### Removed

- `DESIGN.md`, redistributed among the three documents of `docs/`. The history stays available in git.

### Security

- The HMAC key signing the `state` of the CIMD proxy moved from a Lambda environment variable to Secrets Manager, read at runtime. As an environment variable the value sat in clear text.
